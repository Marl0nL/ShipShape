# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Checks: `PYTHON=.venv/bin/python scripts/check` is what CI runs, less the `classic_herdr` tests (below) (shellcheck, ruff, pytest, npm test, public-repo hygiene). The repo is public: read `docs/hygiene.md`; only placeholder names, `example.com`/`example.invalid` and documentation address ranges in code, docs, tests and screenshots.
- On a busy Ship the full check takes over 10 minutes: run it in the background, and prefer targeted tests while you work.
- pytest runs in parallel workers (pytest-xdist; `SHIPSHAPE_TEST_WORKERS`, default 4, 1 for serial): a test may share no fixed path, port or folder with another. Use `tmp_path`, `short_dir` for sockets, `fl_harness.start_sshd` for a real sshd, and bind port 0 rather than picking a port to bind later. Mark a test that exists only for classic herdr `classic_herdr`: `scripts/check` skips those unless `SHIPSHAPE_TEST_CLASSIC_HERDR=1` (CI sets it).
- FleetLedger tests touch no network: the autouse guard in `fleetledger/tests/fl_netguard.py` fails a test that looks a name up, connects off this computer or runs the real ssh. Inject fakes (`FakeSSH`; `fl_harness.no_ship_answers` for a test that starts the real poller through `server.serve`); mark only deliberate cases `real_resolver` or `local_sshd`. In these tests `os.fsync`/`os.sync` return at once (mark `real_sync` for the real calls) and `home`'s keys are copies from a per-worker pool.
- Ship code (`ship/`) is tested in a sandbox root with fake `hc`, `herdr`, `claude`, `gh`, ... (`ship/tests/ship_harness.py`, `ship/tests/fakes/fake.py`); never drive a real herdr from tests. FleetLedger reaches Ships only through `ship-ctl` (`contracts/ship-ctl.md`); schema changes go in both `contracts/` and their copies in `ship/schemas/` (a test keeps them identical).
- Ship agents: ShipShape's agent record (`ship/lib/shipctl/record.py`, `/var/lib/shipshape/agents.json`) decides what resumes after a boot and what restarts after a crash; herdr's own resume is off. Only `ship/lib/shipctl/runtime.py` runs `herdr` or herdr-core's `hc` (`Herdr`/`Core`, picked by ship.toml `runtime`): add runtime calls there, never `herdr`/`hc` argv elsewhere; core agents start through `ship/files/bin/agent-launch`; every claude launch ends with `naming.remote_control_args` (Remote Control only for the agents the record gives it to, `contracts/settings.md`); and nothing may call `hc kill` or `hc server stop` (both end agents). Sandbox Ships run herdr-core by default (the fake `hc`); `ship.use_herdr()` opts into classic herdr, only in `ship/tests/test_ship_herdr_legacy.py`, the switch tests and `test_ship_core.py`'s cases that move a Ship between runtimes. A live Ship changes runtime only through `ship-ctl runtime switch` (`ship/lib/shipctl/switch.py`, tests in `test_ship_runtime_switch.py`), which stops agents first and rolls back on failure.
- Sign-ins: one file per flow in `ship/signins/` (`contracts/signin.schema.json`), read by FleetLedger (logins, `signinreg.py`) and by the Ship from its bundle (status checks, `ship-ctl signin check`, `shipctl/signins.py`, `signincheck.py`). Add or change a sign-in there, never as a list in code; FleetLedger's post-login check asks the Ship.
- Attaching: herdr Ships use `herdr --remote`, herdr-core Ships `hc` (the herdr TUI cannot attach to core). Every attach command FleetLedger shows comes from `fleetledger/fleetledger/attach.py` (runtime from the Ship's status). The trust bundle's install.sh for a herdr-only fleet must stay byte-identical to the fixtures in `fleetledger/tests/fixtures/install-sh/`.
- UI screenshots: `.venv/bin/python fleetledger/tests/demo_ui.py --port N --home <empty dir>` (a generic one such as `/tmp/fleetledger-demo`: pages can show its paths) serves the web UI against made-up Ships in a throwaway FleetLedger home (unbuffered stdout prints the sign-in link; `--remote` adds the remote web UI and made-up paired devices; `--vault` a locked vault; `--core` makes ship-01 a herdr-core Ship); add new `ship-ctl` verbs to its `make_ssh` when a page needs them. Its sign-ins play the recorded sessions in `fleetledger/tests/fixtures/concierge/` (`demo_spawner`), so one started there waits for you like a real one. PRs embed screenshots from `pr-screenshots/` by raw commit-SHA URL, added in one commit and removed in the next so they never reach `main`.
- Secrets: every read and write goes through `fleetledger/fleetledger/overlay/secret_store.py` (OS keyring, FleetLedger's vault when it is on, or 0600 files; `docs/vault.md`); while the vault is on no secret may go to a file. Where ships.toml records each secret (store, keyring item, file) is one row per secret in `fleetledger/fleetledger/secretplaces.py`: add a new secret there. Tests that turn the vault on lower its scrypt cost and skip the RAM-folder check (`fast` fixture in `fleetledger/tests/test_vault.py`).
- Only one copy acts (`ship-fleet migrate`, standby/retired markers): `handover.refusal` is the one rule. The CLI gates on it at start; the web UI on every request, Ship poll and job (`fleetledger/fleetledger/web/copyguard.py`). Anything new that reaches Ships or changes fleet state asks it there, never a check of its own.
- New FleetLedger state: a file written under FleetLedger's config or data folders must be taught to `ship-fleet migrate` (`_plan_config`/`_plan_data` in `fleetledger/fleetledger/migrate.py`: move it, or leave it with a reason; `handover.wipe_plan` for what a wipe deletes), or every move stops on it as an unknown file. Tests: the two-computer fixtures in `fleetledger/tests/test_migrate.py`.
- Toolkits (a user's own recipes, profiles and sign-ins in a folder outside the repo; `contracts/toolkit.md`): `fleetledger/fleetledger/toolkits.py` loads and checks one; `Catalogue.from_repo(repo, inventory)` merges them as `toolkit/id` (no inventory: the repo catalogue alone); `Catalogue.check_allowed` refuses toolkit ids on a Ship its `only_tags` leave out. FleetLedger packs each one (`toolkitpack.py`) and sends it only through `toolkitpush.py`; on the Ship, `ship/lib/shipctl/toolkits.py` applies it, and ship.toml `[toolkits]` is the allow-list: read toolkit files only through `toolkits.root_of`, never a path or the `current` link. Tests copy the placeholder `fleetledger/tests/fixtures/toolkits/examplekit`; `fleetledger/tests/test_toolkitpush.py` drives real sandbox Ships (`ship_harness.build_ship`).
