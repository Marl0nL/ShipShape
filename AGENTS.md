# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Checks: `PYTHON=.venv/bin/python scripts/check` is exactly what CI runs (shellcheck, ruff, pytest, npm test, public-repo hygiene). The repo is public: read `docs/hygiene.md`; only placeholder names, `example.com`/`example.invalid` and documentation address ranges in code, docs, tests and screenshots.
- Ship code (`ship/`) is tested in a sandbox root with fake `herdr`, `claude`, `gh`, ... (`ship/tests/ship_harness.py`, `ship/tests/fakes/fake.py`); never drive a real herdr from tests. FleetLedger reaches Ships only through `ship-ctl` (`contracts/ship-ctl.md`); schema changes go in both `contracts/` and their copies in `ship/schemas/` (a test keeps them identical).
- Ship agents: ShipShape's agent record (`ship/lib/shipctl/record.py`, `/var/lib/shipshape/agents.json`) decides what resumes after a boot and what restarts after a crash; herdr's own resume is off. Only `ship/lib/shipctl/runtime.py` runs `herdr` or herdr-core's `hc` (`Herdr`/`Core`, picked by ship.toml `runtime`): add runtime calls there, never `herdr`/`hc` argv elsewhere; core agents start through `ship/files/bin/agent-launch`, and nothing may call `hc kill` or `hc server stop` (both end agents). Core paths are tested with the fake `hc` (`ship.use_core()`, `ship/tests/test_ship_core.py`). A live Ship changes runtime only through `ship-ctl runtime switch` (`ship/lib/shipctl/switch.py`, tests in `test_ship_runtime_switch.py`), which stops agents first and rolls back on failure.
- Attaching: herdr Ships use `herdr --remote`, herdr-core Ships `hc` (the herdr TUI cannot attach to core). Every attach command FleetLedger shows comes from `fleetledger/fleetledger/attach.py` (runtime from the Ship's status). The trust bundle's install.sh for a herdr-only fleet must stay byte-identical to the fixtures in `fleetledger/tests/fixtures/install-sh/`.
- UI screenshots: `.venv/bin/python fleetledger/tests/demo_ui.py --port N --home <empty dir>` (a generic one such as `/tmp/fleetledger-demo`: pages can show its paths) serves the web UI against made-up Ships in a throwaway FleetLedger home (unbuffered stdout prints the sign-in link; `--remote` adds the remote web UI and made-up paired devices; `--vault` a locked vault; `--core` makes ship-01 a herdr-core Ship); add new `ship-ctl` verbs to its `make_ssh` when a page needs them. Its sign-ins play the recorded sessions in `fleetledger/tests/fixtures/concierge/` (`demo_spawner`), so one started there waits for you like a real one. PRs embed screenshots from `pr-screenshots/` by raw commit-SHA URL, added in one commit and removed in the next so they never reach `main`.
- Secrets: every read and write goes through `fleetledger/fleetledger/overlay/secret_store.py` (OS keyring, FleetLedger's vault when it is on, or 0600 files; `docs/vault.md`); while the vault is on no secret may go to a file. Tests that turn the vault on lower its scrypt cost and skip the RAM-folder check (`fast` fixture in `fleetledger/tests/test_vault.py`).
- New FleetLedger state: a file written under FleetLedger's config or data folders must be taught to `ship-fleet migrate` (`_plan_config`/`_plan_data` in `fleetledger/fleetledger/migrate.py`: move it, or leave it with a reason; `handover.wipe_plan` for what a wipe deletes), or every move stops on it as an unknown file. Tests: the two-computer fixtures in `fleetledger/tests/test_migrate.py`.

Keep this file for knowledge useful to almost every future agent session in this project.
Do not repeat what the codebase already shows; point to the authoritative file or command instead.
Prefer rewriting or pruning existing entries over appending new ones.
When updating this file, preserve this bar for all agents and keep entries concise.
