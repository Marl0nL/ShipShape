# Seed and bundle contract

How a new Ship gets its identity and its tooling on first boot. The Fleet track
writes seeds and bundles (W3, and `ship-fleet update` for bundles); the Ship track
consumes them (W4 ship-provision, W5 `ship-ctl converge`).

Version 1.

## The seed ISO

A cloud-init NoCloud seed:

- ISO 9660 with Joliet and Rock Ridge, volume identifier `CIDATA`.
- Three files at the root: `user-data`, `meta-data`, `network-config`.
- Attached to the VM as a CD-ROM. On Proxmox it is uploaded to the seed-only
  storage (the upload API accepts ISOs but not cloud-init snippets).
- FleetLedger keeps its local copy at mode 0600 and deletes the uploaded ISO once
  the Ship has enrolled (below).

The only secret in a seed is the Ship's own SSH host private key. Nothing else
secret may ever be added: no tokens, no passwords, no other keys.

### meta-data

```yaml
instance-id: ship-01-3f9a1c2e   # <ship name>-<8 random hex>; new for every seed
local-hostname: ship-01
```

A new seed for the same Ship must use a new `instance-id`, or cloud-init will not
run again.

### network-config

Network config version 2, DHCP on the first Ethernet interface, unless the Ship
needs a static address:

```yaml
version: 2
ethernets:
  primary:
    match:
      name: "e*"
    dhcp4: true
```

### user-data

A `#cloud-config` document with exactly these top-level keys (others are not
allowed, so the Ship track can rely on nothing else happening at first boot):

```yaml
#cloud-config
hostname: ship-01
preserve_hostname: false
ssh_pwauth: false
disable_root: true
ssh_deletekeys: true
ssh_genkeytypes: []            # no other host key types: only the pinned ed25519 key exists
ssh_keys:
  ed25519_private: |
    -----BEGIN OPENSSH PRIVATE KEY-----
    (generated by FleetLedger for this Ship; FleetLedger does not keep it)
    -----END OPENSSH PRIVATE KEY-----
  ed25519_public: ssh-ed25519 AAAA... ship-01
users:                         # no "default" entry: there is no ubuntu user
  - name: fleet
    gecos: ShipShape admin
    shell: /bin/bash
    lock_passwd: true
    sudo: "ALL=(ALL:ALL) NOPASSWD: ALL"
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... fleet-admin        # ships.toml fleet.admin_key (.pub)
  - name: agent
    gecos: ShipShape agent
    shell: /bin/bash
    lock_passwd: true
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... you                # ships.toml fleet.agent_keys
write_files:
  - path: /etc/shipshape/ship.toml
    owner: root:root
    permissions: "0644"
    content: |
      schema = 1
      # ... a document valid against ship.toml.schema.json
  - path: /var/lib/shipshape/bundle.tar.gz
    owner: root:root
    permissions: "0600"
    encoding: b64
    content: H4sIAAAA...                       # the tooling bundle, base64
  - path: /var/lib/shipshape/bundle.sha256
    owner: root:root
    permissions: "0644"
    content: |
      <64 hex>  bundle.tar.gz
runcmd:
  - [bash, -c, "<the bootstrap script below>"]
```

`ssh_authorized_keys` hold public keys only. `ship.toml` must validate against
`ship.toml.schema.json`; the seed generator validates it before writing the ISO.

### Bootstrap (the runcmd)

The seed runs exactly this script; everything else belongs to ship-provision:

```bash
set -euo pipefail
install -d -m 0750 /var/log/shipshape
exec >>/var/log/shipshape/provision.log 2>&1
cd /var/lib/shipshape
sha256sum -c bundle.sha256
tmp="$(mktemp -d)"
tar -xzf bundle.tar.gz -C "$tmp"
release="$(python3 -c 'import json,sys; m=json.load(open(sys.argv[1])); print(m["tooling_version"] + "-" + m["commit"][:12])' "$tmp/bundle.json")"
install -d -m 0755 /opt/shipshape/releases
rm -rf "/opt/shipshape/releases/$release"
mv "$tmp" "/opt/shipshape/releases/$release"
chmod 0755 "/opt/shipshape/releases/$release"
ln -sfn "/opt/shipshape/releases/$release" /opt/shipshape/current
exec /opt/shipshape/current/provision/ship-provision --first-boot
```

`ship-ctl converge --bundle <path>` performs the same unpack-and-switch steps for
an update, then runs `ship-provision --converge`.

## The tooling bundle

A gzip-compressed tar archive with relative paths only (no leading `/`, no `..`).
At its root:

| Entry | Required | What it is |
|---|---|---|
| `bundle.json` | yes | Manifest, valid against `bundle-manifest.schema.json`. |
| `versions.toml` | yes | Copy of the repo's `versions.toml`. |
| `provision/ship-provision` | yes, executable | Takes `--first-boot` or `--converge`; idempotent; exit 0 on success. |
| `bin/ship-ctl` | yes, executable | See `ship-ctl.md`. |
| everything else under the repo's `ship/` | as present | `files/`, `tools/`, `profiles/`, `axi/`, `skills/`, ... |

Excluded: `ship/tests/`, any `node_modules/`, editor and cache files. Keep the
bundle under 5 MB; Node dependencies are installed on the Ship from the pinned
versions, not shipped.

The release folder on the Ship is `<tooling_version>-<first 12 characters of commit>`.
FleetLedger packs the `ship/` tree from the checkout it was installed from and
records that commit; a bundle packed from a dirty tree sets `"dirty": true`.

## Enrolment

1. FleetLedger connects as `fleet` with the host key it generated, so the first
   connection is already verified.
2. It polls `ship-ctl status --json` until `provision.result` is `ok` (or `failed`).
   Until ship-ctl exists, `cloud-init status --format json` stands in.
3. It then detaches the seed CD-ROM, deletes the uploaded ISO through the driver,
   and records the Ship as enrolled in `ships.toml`.
